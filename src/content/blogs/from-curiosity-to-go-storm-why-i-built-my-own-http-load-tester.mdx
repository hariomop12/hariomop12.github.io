## 1. It Started With Curiosity

Bas ek simple curiosity thi — **Go ki goroutines aur channels se actually kitna load generate kar sakte hain?**

Mann tha ki server ko high load deke dekhun ki kya hota hai. Koi bada plan nahi, bas ek experiment.

## 2. I Didn't Really Have a Big Plan

Honestly, mere paas starting mein koi bada product idea nahi tha.

Bas socha:

**"Ek load tester bana ke dekhte hain."**

Kuch banaya, phir usme aur cheezein add karne ka mann hua, aur project dheere dheere bada hota gaya.

## 3. The First Version Was Simple

Starting mein kaam bahut simple tha:

**HTTP requests bhejo → multiple goroutines use karo → responses dekho**

Bas itna hi.

Lekin jab actual mein run kiya, tab concurrency ko practically samajhne ka alag hi maza aaya. 10 goroutines, phir 100, phir 1000 — har baar request rate badhta dekh ke maza aata tha. Par jald hi realization aaya ki concurrency badhana = load test nahi, bas raw speed hai.

## 4. Then the Questions Started

Phir naye questions aane lage:

- Ek machine kitna load generate kar sakti hai?
- Concurrency aur request rate mein difference kya hai?
- Server load hone par latency kaise change hoti hai?
- p95 aur p99 actually kya tell karte hain?
- Agar worker fail ho jaye toh?
- Agar test ko beech mein stop karna ho toh?

Aur har question ke saath project mein kuch naya add hota gaya.

## 5. Go Became the Perfect Playground

Go ki **goroutines, channels, worker pools aur concurrency** ko sirf padhne ke bajay, Go-Storm ke through practically use karne ka chance mila.

Yahi project mere liye Go concurrency ko samajhne ka ek practical playground ban gaya. Pehli baar goroutine leak ka saamna kiya, phir use `context` cancellation se fix kiya — aise hi chhote-chhote real problems se samajh banayi.

## 6. From Request Generator to Load Testing Tool

Jo initially simple HTTP request generator tha, woh gradually proper load testing tool banne laga:

concurrency control → rate limiting → metrics → graceful shutdown → better reporting...

Har feature ke saath project thoda aur useful hota gaya. Ab ye sirf "requests bhejne" wala tool nahi — p50/p95/p99 percentiles, status code distribution, JSON reports sab hai.

## 7. The Moment One Machine Wasn't Enough

Phir ek interesting problem saamne aayi:

**"Agar mujhe aur zyada load generate karna hai toh?"**

Ek point ke baad problem server ki nahi, **meri machine ki** hone lagti hai. Jitni bhi goroutines chalao, CPU, memory aur network bandwidth se bound ho jata hai.

Aur yahin se distributed load testing ka idea aaya.

Ek baar maine 10,000 requests 2 agents ke saath chala kar dekha:

```text
Total Requests: 10000
Successful: 10000
Failed: 0
Success Rate: 100.00%
Avg Response: 11.48ms
p95 Response: 16.48ms
p99 Response: 20.40ms
Requests/sec: 313.98
```

Aur per-agent breakdown se saaf dikhta tha ki kaunse machine ne kitna load handle kiya:

```text
AGENT BREAKDOWN
------------------------------------------------------------
Agent            Requests        Avg        p95    Success
agent-a              4998 11.48ms   16.52ms     100.0%
agent-b              5002 11.48ms   16.47ms     100.0%
```

**Ye story next blog mein.**

## 8. What Go-Storm Looks Like Today

Aaj Go-Storm kaafi evolve ho chuka hai.

Ab ye sirf HTTP requests bhejne wala small experiment nahi hai. Isme load generation, concurrency control, rate limiting, performance metrics aur **distributed testing** jaise concepts aa chuke hain — saath hi live Prometheus metrics aur Grafana dashboard bhi.

Project link → [Go-Storm on GitHub](https://github.com/hariomop12/go-storm)

## 9. Why I'm Still Building It

Main Go-Storm ko k6 ka replacement banane ke intention se nahi bana raha.

Main bas ye samajhna chahta hoon:

> **"Jab hum kisi system ko uski limit tak push karte hain, toh actually andar kya hota hai?"**

Aur Go-Storm mere liye us question ko explore karne ka ek way ban gaya.
